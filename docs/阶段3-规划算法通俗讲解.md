# 阶段 3：规划算法通俗讲解

本文不重复完整代码，而是回答一个更重要的问题：TravelMind 为什么能把一堆地点、天气、路线和预算，变成一份稳定、可检查的日程？

配套代码位于 backend/app/planning/。建议先读本文建立直觉，再按以下顺序对照源码：

1. models.py：规划器接收和返回什么。
2. money.py：怎样统一比较不同币种。
3. scoring.py：怎样筛选并给地点打分。
4. zoning.py：怎样把相近地点装进同一个区域。
5. scheduler.py：怎样把区域排进一天的时间线。
6. planner.py：怎样组织整个流程。
7. repair.py：计划不合格时怎样有限修正。

---

## 1. 先把规划器想成一位旅行管家

这位管家不会凭感觉直接写行程，而是依次做七件事：

1. 收齐事实：旅行请求、地点、天气、路线矩阵、汇率和规划时间。
2. 硬过滤：先删掉明确不能去的候选。
3. 软评分：给剩余地点发一张“适合今天去”的成绩单。
4. 地理分区：把彼此较近、交通可达的地点装进同一个旅行篮子。
5. 日期分配：困难日期先选，例如雨天先拿室内资源丰富的篮子。
6. 单日排程：沿时间轴插入游览、交通、缓冲、午餐和休息。
7. 验收修正：阶段 2 约束引擎负责判卷；不合格时最多移除一个候选并完整重排。

可以把整个系统记成一句话：

> 先排除不可能，再比较更合适；先形成候选计划，再让规则引擎独立验收。

## 2. 为什么输入必须是“事实快照”

PlanningFacts 像一张按下快门得到的照片。照片里包含本次规划需要的全部事实，而且规划期间不会改变。

如果规划器偷偷调用当前时间、实时天气或网络地图，会出现两个问题：

- 同样的请求上午运行和下午运行，结果可能不同。
- 测试失败时无法还原当时到底使用了什么数据。

因此 planned_at 由调用方显式传入，地点使用不可变元组，规划器只读取输入。最终生成时间和规则检查时间也来自 planned_at。

这就是“确定性”的第一层：相同输入，走相同计算路径。

## 3. 硬过滤和软评分不是一回事

### 3.1 硬过滤像安检门

硬条件不参加分数竞争。地点只要违反以下条件之一，就不能进入候选：

- 用户明确排除；
- 用户要求无障碍，而地点的 accessible 不是明确的 True；
- 当天天气恶劣，地点又是纯室外；
- 硬预算模式下，单个地点的团体门票已经超过整趟预算；
- 地点已被修正器加入阻止集合。

假设某个地点评分 200 分，但它在 excluded_place_names 中，它仍然必须被删除。否则“高分”就会覆盖用户明确要求。

### 3.2 软评分像成绩单

通过安检的地点才会进入 score_place。当前公式可以概括为：

~~~text
总分
= 地点评分 × 10
+ 兴趣匹配奖励
- 软避开惩罚
+ 天气适配
- 门票预算占比惩罚
+ 必去地点奖励
~~~

各项含义如下：

| 项目 | 直觉 | 当前规则 |
| --- | --- | --- |
| 地点评分 | 大众口碑基础 | rating × 10，缺失时按 2.5 |
| 兴趣 | 越符合用户喜好越靠前 | 每个兴趣 40 × 权重 |
| 软避开 | 不喜欢但并非绝对禁止 | 每项减 80 |
| 天气 | 雨天偏室内，晴天鼓励户外 | 室内 +25、mixed -30、晴天户外 +10 |
| 门票 | 预算占比越高，扣分越多 | 团体门票 ÷ 总预算 × 200，最多扣 200 |
| 必去 | 尽量保证进入计划 | 加 500 |

以固定东京样例中的秋叶原为例：

~~~text
基础评分：4.5 × 10 = 45
动漫兴趣：40 × 1.0 = 40
城市漫步：40 × 0.7 = 28
门票：免费，惩罚 0
总分：45 + 40 + 28 = 113
~~~

活动 priority 最终限制在 1 到 100，所以它在日程中的优先级为 100，但 CandidateScore 仍保留原始 113 分用于排序。

每次加减分都会写进 reasons。这让前端以后可以解释“为什么推荐”，测试也能验证算法依据。

### 3.3 相同分数为什么还要比较 ID

如果两个地点都是 80 分，仅按分数排序可能依赖输入顺序。代码使用：

~~~text
先按分数从高到低，再按 place_id 从小到大
~~~

这叫“稳定兜底规则”。它保证 fixture 即使倒序传入，也能产生相同结果。

## 4. 金额为什么使用最小货币单位和 Decimal

Money.amount 保存的是最小货币单位：

- CNY 的 100 表示 1 元；
- JPY 没有分，100 表示 100 日元。

这样做可以避免 0.1 + 0.2 一类浮点误差。换汇时也不直接使用 float 连乘，而是先转成 Decimal，再使用 ROUND_HALF_UP 舍入到整数最小单位。

固定样例规定：

~~~text
1 JPY 最小单位 = 4.8 个 CNY 最小单位（分）
~~~

两名旅行者购买每人 1000 JPY 的门票：

~~~text
单人：1000 × 4.8 = 4800 分
两人：4800 × 2 = 9600 分，即 96 元
~~~

汇率缺失时直接抛出 MissingExchangeRateError，而不是偷偷按 1:1。明确失败比得到一份看似合理、实际金额错误的行程更安全。

## 5. 地理分区：把散落地点装进旅行篮子

如果每天从城市东边跑到西边，再返回东边，即使每个地点都很喜欢，体验也很差。因此规划器先把地点聚成若干 Zone。

### 5.1 经纬度距离：把地球看成球

普通平面直线距离不适合直接计算经纬度。haversine_km 使用 Haversine 公式估算球面上两点的弧线距离。

不必背公式。可以想象用一根细线贴着地球表面，连接两个地点，代码求的是这根线的长度。

### 5.2 凝聚聚类：从一个地点一个岛开始

build_zones 使用一种简单的凝聚式聚类：

1. 开始时，每个地点都是一个独立区域。
2. 枚举任意两个区域。
3. 优先选择区域之间存在可用路线的组合。
4. 在同类组合里，选择最近的一对。
5. 合并它们。
6. 重复，直到区域数量达到目标。

两个区域之间的距离取“跨区域最近两个地点”的距离。这叫单链接思想。它简单直观，适合当前 10 到 30 个单城市 POI 的 MVP。

合并选择使用三层排序：

~~~text
有没有路线事实 → 地理距离 → 稳定 ID
~~~

因此它既参考地图位置，也参考路线矩阵，而且不会因为集合遍历顺序不同而随机变化。

### 5.3 一个四地点小例子

假设有 A、B、C、D：

- A 到 B 相距 0.8 km 且有路线；
- C 到 D 相距 1.0 km 且有路线；
- B 到 C 相距 2.0 km 但路线缺失。

如果目标是两个区域，算法会先合并 A+B，再合并 C+D，得到两个适合分别安排一天的旅行篮子。

注意：这不是数学上的全局最优解。它的目标是规则简单、结果稳定、容易解释。

## 6. 日期分配：先照顾最难安排的那一天

assign_zones_to_days 不按日期顺序直接分配，而是先给日期排“困难度”：

~~~text
恶劣天气 → 天气未知 → 尚可 → 良好
~~~

雨天最受限制，所以先选择在雨天得分总和最高的区域。由于纯室外地点已经被硬过滤，而室内地点还有 +25 奖励，室内资源丰富的区域通常会被雨天选中。

这和考试排座位很像：先安排限制最多的学生，剩下的人更容易找到位置。算法领域常称为“最受约束者优先”。

选区时计算某区域内所有地点在当天的分数和，分数最高的区域胜出；同分时用 zone.id 决定。

![雨天优先分区](/images/雨天优先分区.png)

## 7. 单日路线：可达候选中的贪心选择

一个区域分给某天后，DayScheduler 还要决定访问顺序。

当前策略是：

1. 第一个地点选当天分数最高者。
2. 从当前位置出发，只查看路线矩阵中可达的剩余地点。
3. 在可达地点中选分数最高者。
4. 重复，直到没有可达候选。

它叫“贪心”，因为每一步只做眼前最合适的选择，不枚举所有可能路线。

### 为什么 MVP 选择贪心

如果一天有 n 个地点，穷举所有顺序接近 n!。地点一多，组合数量增长很快。贪心算法速度快、行为容易解释，也足以证明完整业务链路。

### 贪心的局限

最高分地点可能把路线带到城市一角，导致后续几个中等分地点无法安排。所以贪心不保证全局最优。后续可以升级为：

- Beam Search：每一步保留若干条较好的部分路线；
- 动态规划：适合规模较小且状态定义清晰的场景；
- OR-Tools / CP-SAT：把时间窗、预算和路线统一建模求解。

当前阶段最重要的是“稳定地产生可检查方案”，而不是声称已经找到理论最优行程。

## 8. 时间排程：沿着一根时间尺向右移动

scheduler.py 中的 cursor 可以理解成时间尺上的指针。一天从 daily_start_time 开始，每插入一段内容，指针就向右移动。

安排一个非首站地点时，完整时间关系是：

~~~text
当前位置
→ 交通 route.duration_minutes
→ 最小换乘缓冲 minimum_transfer_buffer_minutes
→ 等待开门（如有）
→ 游览 estimated_visit_minutes
~~~

只有游览结束不晚于闭馆时间和 daily_end_time，地点才会被放入当天。

例如：

~~~text
09:00–11:00  游览 A
11:00–11:20  前往 B
11:20–11:30  换乘缓冲
11:30–12:30  游览 B
12:30–13:30  午餐
13:30–14:30  休息
~~~

交通 Activity 和 RouteLeg 分开保存：

- Activity 用于统一展示时间轴；
- RouteLeg 保存距离、步行、费用、交通方式等路线事实；
- Activity.route_leg_id 把二者连接起来。

缺少营业时间不会被当作确认全天营业。排程器可以暂时放入，但阶段 2 会产生 DATA_INCOMPLETE warning，让调用方知道数据仍需补齐。

### 午餐与休息为什么预留活动名额

max_activities_per_day 的口径包含游览、用餐和休息。排程器先为午餐保留一个槽位，有休息要求时再保留一个，剩余槽位才分给 Visit，避免“景点塞满后违反活动数量规则”。

## 9. 步行上限如何提前阻止违规

每加入一条路线前，排程器计算：

~~~text
预计累计步行 = 当前累计步行 + 新路线步行
~~~

如果用户设置了 max_walking_meters_per_day，且预计值超过上限，这个下一站会被跳过，路线和活动都不会插入。

这属于“生成时防错”。阶段 2 的 MAX_WALKING_EXCEEDED 规则仍会再次检查，形成双保险：

- 规划器尽量不制造错误；
- 约束引擎独立验证实际输出。

## 10. 预算与统计为什么必须从明细重算

DayStatistics 和 BudgetSummary 都是派生数据，也就是“缓存”。缓存不能成为另一个真相来源。

每天结束时：

- walking_meters 从 RouteLeg 求和；
- transfer_minutes 从路线时长求和；
- planned_minutes 从非交通活动时长求和；
- estimated_cost 从当天 BudgetItem 求和。

整趟行程结束时：

- planned_total 从所有预算明细求和；
- totals_by_category 按 admission、food、local_transport 等分类求和；
- remaining_amount = limit - planned_total；
- remaining_amount 大于等于 0 时 within_budget 为 True。

因此预算刚好用完是合法的：剩余 0 仍在预算内。

如果修正时只删除一个 Visit，却不重算交通、统计和预算，会留下悬空引用或旧金额。阶段 3 不在旧行程上打补丁，而是改变候选集合后完整重建。

## 11. 约束引擎和规划器的关系：出卷人与判卷人分开

规划器负责“提出一份候选答案”，阶段 2 的约束引擎负责“独立判卷”。

这是有意的职责分离：

| 组件 | 职责 |
| --- | --- |
| planning | 生成尽可能合理的行程 |
| constraints | 检查行程是否违反硬规则 |
| domain | 定义双方共同遵守的数据契约 |

如果规划器自己宣布“我生成的肯定正确”，很容易漏掉边界条件。独立约束引擎会检查日期、重叠、闭馆、交通缓冲、天气、预算、活动数量、步行等规则。

warning 不等于失败。ConstraintReport.passed 只受 error 影响，所以缺少营业时间可以作为警告保留，而不会触发无意义的删除。

## 12. 有限修正：失败后删谁，为什么不会死循环

如果规则报告包含 error，choose_repair 会读取结构化 ConstraintCode，而不是解析中文错误消息。

当前修正过程如下：

1. 取第一个 error。
2. 某些错误不可自动修正，例如输入日期越界、数据不完整、必去地点缺失。
3. 预算超限时可从全程选择候选；其他错误优先看发生错误的当天。
4. 排除必去和 locked 的 Visit。
5. 先选 priority 较低者；同优先级时先选费用较高者；最后用 UUID 稳定兜底。
6. 把这个 place_id 加入 blocked 集合。
7. 从评分、分区、排程、预算开始完整重建。

PlannerConfig.max_repair_rounds 默认是 3，所以最多尝试 4 次：

~~~text
首次生成 + 最多 3 次修正
~~~

如果仍然失败，返回 UNSATISFIED、最后一份 Itinerary、ConstraintReport、attempts 和 repair_notes。它不会抛出模糊错误，也不会无限循环。

固定样例把总预算降到 500 元时，规划器经过三轮修正移除费用较高且优先级较低的地点，第四次得到 433.60 元的可行方案。这正是有限修正的端到端例子。

## 13. 确定性到底由哪些细节保证

相同输入得到相同 JSON，并不是只靠“不联网”，还依赖很多小约定：

- planned_at 显式传入，不读取 datetime.now()；
- 所有派生 ID 使用 UUID5，根据业务内容生成；
- 地点、区域、候选同分时都有稳定 ID 兜底；
- 聚类从按 ID 排序的初始集合开始；
- 金额使用 Decimal 和固定舍入规则；
- 修正每轮只阻止一个确定地点；
- 输入不被原地修改；
- fixture 中天气、路线、汇率和来源时间固定。

UUID5 可以理解为“给同一段业务指纹盖同一个章”。相同日期、地点和活动类型会得到同一个 UUID；UUID4 则像每次随机抽签，不适合可重复测试。

## 14. 怎样对照代码调试一次规划

遇到“某地点为什么没进去”，按以下顺序查最快：

1. scoring.is_eligible：是不是被硬过滤。
2. scoring.score_place：得分和 reasons 是什么。
3. zoning.build_zones：它被分到了哪个区域。
4. planner.assign_zones_to_days：该区域分给了哪一天。
5. scheduler._order_candidates：前一地点到它是否有可用路线。
6. scheduler._fit_visit：营业时间和每日时间窗是否放得下。
7. 步行上限：加入该路线后是否超限。
8. ConstraintReport：最终是否被规则引擎判错。
9. repair_notes：是否在修正轮次中被阻止。

遇到“金额不对”，按以下顺序查：

1. 原始 Money 的币种和最小单位；
2. ExchangeRate 的 key 和含义；
3. 是否先换算再乘 travelers；
4. 是否生成正确 BudgetItem；
5. BudgetSummary 是否由明细重算。

## 15. 当前算法做到了什么，还没有做到什么

### 已做到

- 无网络、无数据库、无 LLM 的纯 Python 规划；
- 硬过滤和可解释软评分；
- 天气感知的地点排序与日期分配；
- 同时考虑坐标和路线事实的确定性分区；
- 营业时间、交通缓冲、步行、餐休和每日时间窗排程；
- 多币种金额换算和预算汇总；
- 使用阶段 2 引擎验收；
- 有上限、可解释的自动修正；
- 相同输入产生相同结果。

### 尚未做到

- 不保证全局最优路线；
- 不搜索饭店、酒店或实时车次；
- 不处理预约库存和精确入场时段；
- 不考虑跨城市、多日交通或行李；
- 不对缺失路线做地图估算；
- 修正策略目前只有“阻止一个非必去地点并重建”；
- 没有把规划器暴露为阶段 4 API，也没有前端编辑交互。

这些不是阶段 3 未完成，而是明确留给后续阶段的能力边界。

## 16. 推荐学习练习

为了真正掌握算法，可以依次做下面的实验，每次只改一个输入并观察输出：

1. 把某兴趣权重从 1.0 改成 0.2，观察候选分数和日期安排。
2. 把某天改成 poor，观察纯室外地点是否消失。
3. 把 max_walking_meters_per_day 降到 1000，检查路线数量。
4. 把预算设为 50000，观察 repair_notes 和 attempts。
5. 把 max_repair_rounds 设为 0，确认第一次失败后立即 UNSATISFIED。
6. 把同一组 places 倒序输入，确认结果仍完全一致。
7. 删除 JPY/CNY 汇率，观察明确的 MissingExchangeRateError。
8. 把一个地点设置为当天 closed，确认不会被排入日程。

掌握阶段 3 的标志不是记住每一行代码，而是能回答：

- 哪些条件必须硬过滤，哪些适合用分数表达？
- 为什么要先处理雨天？
- 为什么分区同时看路线和坐标？
