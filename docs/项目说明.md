## 1. 项目总体目标

这两个项目分别面向两个不同场景：

- **动态旅行规划 Agent**：消费级 Agent，重点体现 Tool Calling、实时信息获取、状态管理、约束规划、Human-in-the-loop 和 MCP。
- **Autonomous Debugging Agent**：开发者 Agent，重点体现代码理解、假设生成、证据验证、沙箱执行、自动修复、测试回归、Checkpoint 和 Agent Evaluation。

建议不要将二者做成“聊天框 + 大模型接口”的普通应用，而是突出真正的 Agent 特征：

```text
LLM
+
Tools
+
State
+
Planning
+
Feedback Loop
+
Execution
+
Evaluation
```

## 2. 项目一：动态旅行规划 Agent

### 2.1 项目名称建议

可选名称：

- TravelMind
- TripPilot
- RoamAgent
- PlanGo
- WanderFlow

推荐名称：

> **TravelMind — Dynamic Travel Planning Agent**

---

### 2.2 项目定位

用户输入：

- 出发地
- 目的地
- 出行日期
- 出行人数
- 总预算
- 兴趣偏好
- 饮食偏好
- 交通偏好
- 住宿偏好

Agent 根据实时天气、景点情况、交通距离、预算和用户偏好生成初步方案。

用户可以继续提出修改意见，例如：

> 我不想每天走太多路。

> 我想增加一天动漫相关行程。

> 第二天下雨，帮我把户外景点调整一下。

> 酒店预算太高了，帮我重新规划。

Agent 根据用户最新约束重新规划，并最终生成一份完整、结构化的旅行计划。

---

### 2.3 项目核心特色

普通旅游助手：

```text
用户输入
↓
LLM
↓
一次性生成攻略
```

TravelMind：

```text
用户需求
↓
约束解析
↓
实时信息查询
↓
候选景点筛选
↓
路线规划
↓
预算评估
↓
冲突检测
↓
初步方案
↓
用户反馈
↓
动态重新规划
↓
最终旅行计划
```

核心亮点是：

> **旅行计划不是一次生成，而是根据实时数据和用户持续反馈动态调整。**

### 2.4 目标用户

- 自由行用户
- 第一次去某城市的游客
- 预算有限的学生用户
- 有明确兴趣偏好的旅行者
- 不愿意手动整理几十篇攻略的用户

### 2.5 核心使用流程

#### Step 1：创建旅行

用户填写：

```text
出发地：南京
目的地：东京
日期：2026-10-01 ~ 2026-10-05
人数：2
总预算：10000 元

兴趣：
动漫
美食
城市漫步

不喜欢：
购物

住宿偏好：
交通方便
```

---

#### Step 2：Agent 提取约束

统一转换为结构化状态：

```json
{
  "origin": "南京",
  "destination": "东京",
  "start_date": "2026-10-01",
  "end_date": "2026-10-05",
  "travelers": 2,
  "budget": 10000,
  "preferences": [
    "动漫",
    "美食",
    "城市漫步"
  ],
  "avoid": [
    "购物"
  ]
}
```

---

#### Step 3：查询实时信息

Agent 调用：

```text
Weather Tool
POI Tool
Map Tool
Search Tool
Hotel Tool
Transportation Tool
```

获取：

- 每日天气
- 景点开放时间
- 景点位置
- 门票
- 推荐游览时间
- 景点之间距离
- 交通时间
- 酒店价格参考
- 当地活动
- 临时闭馆或维修情况

---

#### Step 4：生成初始计划

例如：

```text
Day 1
浅草寺
上野
秋叶原

Day 2
镰仓
江之岛

Day 3
新宿
涩谷
代官山

Day 4
东京国立博物馆
东京站
银座

Day 5
自由活动
返程
```

---

#### Step 5：约束检查

Constraint Engine 检查：

```text
天气冲突
景点闭馆
预算超限
移动距离过长
时间安排过密
交通时间不足
住宿位置不合理
预约冲突
```

例如：

```text
发现：
10 月 2 日降雨概率较高。

问题：
当天安排镰仓 + 江之岛户外行程。

建议：
将镰仓调整至 10 月 3 日，
10 月 2 日替换为室内活动。
```

---

#### Step 6：用户反馈

用户：

> 我还是想看镰仓日落。

Agent重新计算：

```text
天气
↓
日落时间
↓
交通时间
↓
景点开放时间
↓
重新排列 Day 2 / Day 3
```

---

#### Step 7：最终输出

最终生成：

- 每日路线
- 时间安排
- 景点
- 餐饮建议
- 交通方式
- 天气
- 每日预算
- 总预算
- 注意事项

### 2.6 核心功能模块

#### 2.6.1 用户需求管理

支持用户填写：

```text
目的地
日期
预算
人数
出发地
兴趣偏好
住宿偏好
交通偏好
饮食偏好
不希望出现的活动
每天最大步行量
每日最晚结束时间
```

---

#### 2.6.2 Weather Tool

输入：

```json
{
  "city": "Tokyo",
  "date": "2026-10-02"
}
```

输出：

```json
{
  "condition": "rain",
  "temperature": 22,
  "rain_probability": 0.75
}
```

Agent 可以根据天气自动调整：

```text
户外 → 室内
海边 → 博物馆
徒步 → 商场 / 展馆
```

---

#### 2.6.3 POI Tool

查询：

```text
景点
餐厅
博物馆
公园
商业街
特色区域
```

返回：

```json
{
  "name": "浅草寺",
  "category": "景点",
  "rating": 4.7,
  "open_time": "06:00",
  "close_time": "17:00",
  "estimated_duration": 120
}
```

---

#### 2.6.4 Map Tool

负责：

```text
路线距离
公共交通时间
步行时间
景点聚类
地理位置排序
```

目标：

避免出现：

```text
上午浅草
下午横滨
晚上吉祥寺
```

这种不合理路线。

---

#### 2.6.5 Budget Tool

建立预算：

```text
总预算
├── 交通
├── 住宿
├── 餐饮
├── 景点门票
├── 市内交通
└── 弹性预算
```

示例：

```text
预算：10000 元

机票：3000
住宿：3200
交通：800
餐饮：1500
门票：600

剩余：900
```

---

#### 2.6.6 Constraint Engine

不要完全依赖 LLM。

一些规则应该由程序确定：

```text
景点开放时间
交通时间
预算
日期
天气
距离
最大步行量
每日结束时间
```

可以采用：

```python
Rule Engine
+
LLM Planning
```

---

#### 2.6.7 Dynamic Replanning

这是项目最重要的功能。

场景：

```text
用户：
我今天起晚了，现在 11:30。
```

Agent：

```text
读取今日计划
↓
读取当前时间
↓
计算剩余时间
↓
保留高优先级景点
↓
删除低优先级景点
↓
重新计算交通
↓
生成新计划
```

另一个场景：

```text
明天下雨
```

Agent：

```text
识别户外景点
↓
寻找室内替代方案
↓
重新安排未来行程
```

### 2.7 Agent 工作流

推荐使用 LangGraph。

```text
START
  │
  ▼
Parse User Request
  │
  ▼
Build Trip State
  │
  ▼
Research
  │
  ├── Weather
  ├── POI
  ├── Map
  ├── Search
  └── Hotel
  │
  ▼
Planner
  │
  ▼
Constraint Check
  │
  ├── Pass
  │     ↓
  │   Draft Plan
  │
  └── Fail
        ↓
      Replan
        │
        └──────→ Constraint Check
  │
  ▼
User Review
  │
  ├── Accept
  │      ↓
  │    Finalize
  │
  └── Modify
         ↓
      Update State
         ↓
       Replan
```
